# 文档树：主文档 ↔ 分文档

> 在 **建或改步骤文档 / 定稿归档** 时按需加载。
> 一套任务 = 一份主文档 + N 份分文档。核心问题只有一个：**改了一份，另一份还是对的吗？**

## 一、结构

```
.spec-pact/
├── plan.md                      ← 主文档：任务总纲 + 步骤总表 + 文档注册表
├── steps/
│   ├── 01-scope/
│   │   ├── step.md              ← 分文档：该步的目标 / 验收 / 执行记录
│   │   └── notes/               ← 该步过程笔记（可选）
│   └── 02-design/
│       └── step.md
├── decisions.md                 ← 决策日志（为什么）
├── changes.md                   ← 改动流水（改了什么）
├── refs.md                      ← 外部只读引用登记
├── state.json                   ← 状态机（脚本写）
└── snapshots/                   ← 回滚锚点
```

## 二、主文档 `plan.md` 骨架

```markdown
# <任务名>

> status: execute
> updated: 2026-10-28 21:20
> plan_version: 1

## 一、任务定义
## 二、目标 / 非目标（边界）
## 三、步骤总表          ← 三向一致性的锚点 A
| id | 名称 | 依赖 | 状态 | 验收要点 | 分文档 |
|----|------|------|------|---------|--------|
| 01-scope | 范围确认 | - | done | 边界无歧义 | steps/01-scope/step.md |
| 02-design | 方案设计 | 01-scope | execute | 两方案对比 | steps/02-design/step.md |
## 四、文档注册表        ← 主/分引用总账
| 路径 | 职责 | 状态 | 最后校验 |
## 五、决策索引          ← 链到 decisions.md
## 六、风险与 Plan B
```

## 三、分文档 `step.md` 骨架

```markdown
# 02-design 方案设计

> parent: ../../plan.md
> status: execute              ← 锚点 B
> updated: 2026-10-28 21:20
> upstream_check: 2026-10-28 21:20    ← 最近一次回查主文档
> pending_sync: 无             ← 本次更新导致主文档哪里要改

## 目标
## 输入（含外部只读引用 id，如 r01）
## 输出（落 work/ 还是 output/，文件名）
## 执行标准
- [ ] 机械项：output/design.md 存在且含「方案对比」小节
- [ ] 机械项：sp.py lint 退出码 0
- [ ] 人工项：两方案取舍理由可复述
## 执行记录
- turn 1 (+1): 读完 r01，列出一版候选方案
- turn 4 (-1): 推翻方案 A，因为扩展成本被低估
```

## 四、三向一致性（核心机制）

同一个"步骤状态"出现在三处，必须相等：

| 锚点 | 位置 | 谁写 |
|---|---|---|
| **A** | `plan.md` §三 步骤总表 的 `状态` 列 | 人 / AI 按协议改 |
| **B** | `steps/NN-slug/step.md` 的 `status` | AI 改 |
| **C** | `state.json` 的 `steps[id].phase` | **脚本写，唯一权威** |

```bash
python scripts/sp.py sync
```

不符即报 `conflict` 并列出三方差异（exit 2）。**先修一致性，再推进。**

> 为什么必须机械校验：文档说 done、状态说 execute 这种漂移，靠人眼和 LLM 自觉都不可靠。

## 五、向上校验（改完分文档必须做）

每次更新 `step.md` 后回答两件事：

1. 主文档里哪些描述因此失效？（步骤总表状态、文档注册表、风险清单、决策索引）
2. 落地：改主文档对应处 → 把 `upstream_check` 置为当前时间 → `pending_sync` 清空或列出暂不处理项（须注明理由）

**漏做向上校验 = 文档树开始腐烂的起点。**

## 六、向下校验

主文档步骤总表状态改了 → 对应分文档 `status` 同步 → `sp.py sync` 复核。双向都通，三向才稳。

## 七、归档：就地冻结，不搬家

| 事件 | 动作 |
|---|---|
| 单个步骤完成 | `sp.py archive <id>`：`state.json` 标 `frozen`、`step.md` 置 `done`，**路径不变**，内容只读 |
| 整个任务结束 | `sp.py handoff` 打自包含包；需要留痕时再另存一份冻结副本 |

> **v1 的做法（整个目录 `mv` 进 `archive/`）已废弃**：一移动，`plan.md` 里的 `steps/01-scope/step.md` 全部悬挂，和"引用策略"直接冲突。**路径稳定性优先于归档整洁。**

## 八、计划变更（初始化之后要改步骤时）

步骤总表在初始化时由用户确认并冻结基线（`plan_version`）。之后任何增删改，走三步：

1. `sp.py decision --text "为什么加/删/改这一步"` （这是决策，不是改动）
2. `plan_version + 1`
3. 更新主文档步骤总表 + 受影响的分文档

违反这条就是"计划漂移"——最典型的症状是：做着做着多出一堆没人记得是谁加的步骤。
